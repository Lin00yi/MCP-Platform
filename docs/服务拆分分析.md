## 0. 结论（先看这段）

| 结论 | 内容 |
|---|---|
| **现在有几个服务** | 物理上 **1 个** Spring Boot 进程（`mcp-gateway`，181 文件 / 21.4k 行）+ 1 个前端 SPA + MySQL。逻辑上可切出 **14 个职责域**（见 §2） |
| **建议拆几个** | **2 个后端服务 + 1 个前端 + 1 个共享内核 jar**；另可选 1 个 worker |
| **先拆哪个** | **先拆控制面（Admin）**，不是数据面。数据面是入口、状态最多、风险最高，必须最后动 |
| **不建议拆** | 发现（discovery）、身份（identity）、暴露治理（exposure）、审计（audit）——拆了只会复制逻辑，不产生独立价值 |
| **最大拦路石** | 不是包结构，而是 **11 处进程内状态**（session / SSE / 上游会话 / 缓存）。不先外置，拆完也没法多副本 |

目标形态：

```

   AI 客户端 ─────▶ │ S1 mcp-dataplane      :8081  │ ──▶ 上游 REST / MCP Server
```

## 1. 现状：物理 1 个进程，逻辑 5 条入口

### 1.1 部署现状

原部署只有 3 个单元：MySQL、`backend`（单实例，端口 8081）、静态控制台（反向代理托管）。
反向代理把 `/api/*` 和 `/mcp/*` **都转发到同一个 backend**，所以拆服务在网关层天然可切分。

## 3. 拆分判据与打分

判据（每项 1–5 分，分越高越该拆）：

- **A 独立扩缩容**：流量模型是否与其它域不同？
- **B 故障隔离**：挂掉是否会连坐？
- **C 发布节奏**：改动频率是否独立？
- **D 安全边界**：是否面对不可信输入 / 不同认证体系？
- **E 改造成本**（反向计分：成本越低分越高）

| 职责域 | A | B | C | D | E | 合计 | 结论 |
|---|---|---|---|---|---|---|---|
| D1+D2+D3 数据面 | 5 | 5 | 4 | 5 | 2 | **21** | ✅ 拆（S1） |
| D6~D10 控制面（拓扑/CRUD/审批/账号/导入） | 2 | 4 | 5 | 4 | 5 | **20** | ✅ 拆（S2），POI 随之移出数据面 |
| D5 发现 | 1 | 3 | 3 | 4 | 3 | 14 | ❌ 并入 S1（只读、与数据面同认证同依赖） |
| D12 健康探活 | 3 | 2 | 2 | 1 | 2 | 10 | ⚠️ 先 Redis 锁，可后置 worker |
| D11 审计 | 3 | 2 | 2 | 1 | 3 | 11 | ⚠️ 先异步化，不拆服务 |
| D4 身份 | 1 | 2 | 1 | 3 | 2 | 9 | ❌ 是 SPI，不是服务 |
| D2 暴露治理 | 1 | 1 | 1 | 1 | 2 | 6 | ❌ 共享内核（S1、S2 都在用） |
| D13 控制台 | — | — | — | — | — | — | 已是独立部署单元 |
| D14 客户端 | — | — | — | — | — | — | 不是服务 |

**关键判断：数据面和控制面的分差很小，但拆的先后顺序必须反过来——先拆低风险的 S2。**

## 4. 推荐方案：2 服务 + 1 内核（+2 可选）

### 4.1 S1 `mcp-dataplane`（数据面）

| 项 | 内容 |
|---|---|
| 职责 | MCP 协议接入、会话/SSE、工具目录与暴露、上游 MCP/REST 转发、调用日志写入、客户端发现 |
| 入口 | `/mcp/e/**`、`/mcp/v1/**`（建议随拆分下线）、`/mcp/discovery/**` |
| 认证 | `x-dsh-auth-token` → `UserTokenStore` |
| 依赖 | MySQL（读资产/拓扑，写 `tool_call_record`/`mcp_request_log`）、Redis、user-center（token）、上游系统 |
| 配置 | `MCP_IDENTITY_*`、`MCP_TOOLS_*`、`MCP_EMBEDDING_*`、`MCP_SECURITY_*` |
| 扩缩容 | 2~N 副本，需 Redis 会话 + 上游会话亲和 |
| 不含 | 后台 JWT、POI、springdoc（可关）、审批、账号 |

### 4.2 S2 `mcp-admin`（控制面）

| 项 | 内容 |
|---|---|
| 职责 | 资产 CRUD、拓扑维护、OpenAPI 导入、审批、账号权限、审计查询、健康展示、运维日志 |
| 入口 | `/mcp/admin/**`、`/mcp/log/**`、`/v3/api-docs` |
| 认证 | 后台 JWT + RBAC（`admin_user`） |
| 依赖 | MySQL（读写）、Redis（读 S1 健康/缓存，可选） |
| 配置 | `MCP_ADMIN_JWT_SECRET`、`MCP_ADMIN_INIT_PASSWORD`、`MCP_LOG_*` |
| 副本 | 单写多读；无长连接，2 副本足够 |
| 不含 | 用户 token 校验、上游代理、SSE |

### 4.3 K `mcp-shared`（共享内核 jar）

`entity` / `mapper`(+XML) / `dto` / `enums` / `constants` / `utils` / `identity` / `exposure` / `access`（读侧） / `discovery`（读服务） / `health`（读+探测）。

> **注意**：`admin` 也在用 `exposure`（`McpAdminController` 里用全限定名引用了 `ToolAccessPolicy`、`ToolEmbeddingService`、`ToolPaginationTelemetry` 等），所以 `exposure` 只能进内核，不能只归数据面。

### 4.4 W `mcp-worker`（可选，P4）

探活（30s 全量）、日志清理（03:15）、embedding 重建、预算告警。这三种任务都是「全量 + 定时 + 不应按副本放大」。

**建议：先不建服务**，在 S1 内用 Redis 分布式锁选主执行；等出现「批量重索引 / 大导出」这类重任务再拆。

### 4.5 R `mcp-registry`（可选，按需）

仅当需要**对外公开工具目录**（第三方检索、跨团队商城）时独立。当前发现接口与数据面同源同权，独立只会多一次跳转。

### 4.6 不建议继续往下拆

| 候选 | 不拆理由 |
|---|---|
| 接入层（会话/SSE） ↔ 执行层（工具调用） | 会多一跳网络延迟，而当前工具调用 P99 才是核心指标 |
| 审计为独立服务 | 现在就是一次同步 insert（`McpServiceImpl:790`），异步化即可解决 90% 问题 |
| 身份为独立服务 | 已经是 `UserTokenStore` SPI，进程外就是 user-center，无需再造 |

## 5. 关键改造点（按代码定位）

### 5.1 消除控制面 → 数据面的反向依赖（P0，必须先做）

| 位置 | 现状 | 改法 |
|---|---|---|
| ``McpAdminController.java:151`` | 注入 `McpService`（`test-connect`、`from-rest`） | 抽 `RestToolInvoker` 到内核；或调 S1 `/internal/tools/test-connect` |
| ``McpAdminController.java:154`` | 注入 `McpServerDynamicControllerManager` | admin 只写库 + 发事件；S1 自己刷新路由 |
| ``McpAdminController.java:157`` | 注入 `ToolChangeNotifier` | 改为接口 `ToolChangePublisher`，本地/Redis 两种实现 |
| ``McpAdminController.java:1798`` | 直接调 `refreshAllServerController()` | 删掉，改「发布 revision 变更」 |
| [`McpAdminDiscoveryController`](../mcp-gateway/mcp-admin/src/main/java/com/mcp/transfer/admin/controller/McpAdminDiscoveryController.java) | 注入 `McpDiscoveryService` | 把 `McpDiscoveryService` 放内核（两边都可实例化） |
| [`McpAdminHealthController`](../mcp-gateway/mcp-admin/src/main/java/com/mcp/transfer/admin/controller/McpAdminHealthController.java) | 注入 `McpServerHealthService` | 已改为 `HealthQueryPort` → 数据面 |
| 工具增删改时的向量索引维护 | 控制面直接调 `ToolEmbeddingService` | 已改为「控制面发 TOOL 事件（带 toolId/op），数据面维护索引」 |

### 5.2 `AccessTopologyService` 读写分离（P0）

``AccessTopologyService`` 同时承担：

- 写：`saveNamespace:133`、`deleteNamespace:175`、`setNamespaceServers:186`、`saveEndpoint:292`、`setEndpointNamespaces:339`
- 读：`resolveScope:368`（纯读，已确认无应用授权）、`discoveryServers:401`

拆成 `EndpointScopeReader`（→ S1/内核）与 `AccessTopologyAdminService`（→ S2）。这两个类之间没有共享可变状态，拆分成本最低。

### 5.3 包结构还需 3 处搬家（P0）

| 现状 | 问题 | 去向 |
|---|---|---|
| `annotation.McpServerDynamicControllerManager` | 名字是注解包，实际是数据面路由 | `gateway.route` |
| `config.filter.McpWebConfig` | 一个 WebConfig 注册了两套拦截器，每个请求都要先判「属于哪面」 | 拆 `McpWebConfig` + `AdminWebConfig` |
| `config.session.AdminAuthContext` / `config.LogCleanupScheduler` | 混在「会话」/「配置」包 | `admin.*` 或 worker |

> 拆完之后，MCP 请求链路上不再有 `AdminAuthInterceptor` 的 `startsWith("/mcp/admin")` 判断（见 ``AdminAuthInterceptor.java:41``），也不再需要 `McpRequestWrapper` 之外的跨面分支。

### 5.4 状态外置（P1，多副本前置条件）

| 状态 | 方案 | 状态 |
|---|---|---|
| MCP session | `mcp:session:{id}` 字符串 + TTL 30 min（`SessionStore`） | ✅ P2 |
| SSE 广播 | 事件走 Pub/Sub `mcp:events:config`，各副本转发**本机** emitter | ✅ P2 |
| 上游 session | Hash `mcp:upstream:{gwSession}`，field=上游名 | ✅ P2 |
| 目录缓存 | **保持进程内** + 事件失效 + 30s revision 兜底轮询 | ✅ P2 |
| 超长结果分片 | 已有 `mcp.tools.chunk-store=redis`，直接打开 | ✅ 已有 |
| 健康探活 | Redis 租约选主（`mcp:health:leader`）+ 结果共享（`mcp:health:probe:{id}`） | ✅ P3 |
| 熔断 / 登录限流 | 保留本地（阈值按副本数分摊） | ✅ 可接受 |

> 目录缓存没有 Redis 化是刻意的：它是 DB 的只读派生数据，跨进程共享反而多一次网络往返；
> 「事件失效 + revision 兜底」已经能保证最终一致。

### 5.5 跨服务变更通知（P1/P2，已落地）

原先是进程内同步调用（`ToolChangeNotifier`），拆服务后改为「事件总线」：

```
admin 写库 → HTTP /internal/config-changed → dataplane（任意副本）
                                                  │
                                        ClusterEventBus.publish
                                    ┌─────────────┴─────────────┐
                                    ▼                           ▼
                             单副本：进程内同步回调        多副本：Redis Pub/Sub
                                    │                           │
                                    └──────────┬────────────────┘
                                               ▼
                                    ConfigChangeApplier
                        失效本地缓存 · 刷新动态路由 · 广播本机 SSE
```

- 事件类型：`TOOL` / `PROMPT` / `RESOURCE` / `ROUTES` / `ALL`；
- 兜底：`RevisionWatcher` 每 30s 比对「行数 + 最大 update_time」，不一致就发 `ALL`，
  即使 Redis 丢消息或控制面通知失败，缓存也会自愈；
- `ToolChangeNotifier` 已删除，单副本与多副本走同一条代码路径。

### 5.6 鉴权契约（拆分的前置风险）

数据面依赖 `UserTokenStore` Bean（注释明确写「由 user-center 提供」）。一旦 S1 独立部署，这个 Bean 就没了，必须二选一：

1. **user-center 暴露 introspection/gRPC**（每次调用加一跳，需缓存 30s）；
2. **user-center 签发短时 JWT，S1 用 JWKS 本地验签**（推荐，零额外跳数，但要处理吊销延迟）；
3. S1 与 user-center 同 Pod / 同进程（等于没拆）。

**这是拆分前必须先和 user-center 对齐的契约，不是代码问题。**

## 8. 待决策项（需要你拍板）

### 8.1 `/mcp/v1/{serverPath}` 是否保留？（已决策：下线）

现在数据面有两套平行实现：`McpServiceImpl`（1,977 行，单 server 直连）与 `McpAggregateService`（1,624 行，Endpoint 聚合）。
Endpoint 模型（`/mcp/e/**`）是新方向。**2026-10-24 已删除旧链路的动态注册/控制器/启动引导**；`McpServiceImpl` 中仅保留 Endpoint 复用的执行方法，剩余旧列表/分页代码列入《待办清单》。

### 8.2 控制面的「发现预览」「测试连通」「embedding 重建」

三个功能都是「管理端界面 + 数据面逻辑」。三种处理方式：

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 内核库（共享 jar） | 无网络跳转 | 逻辑双份实例化，配置要两边都有 | 发现预览 ✅ |
| S1 内部 API | 单一实现 | 多一跳，S1 挂了管理端不可用 | 测试连通 ✅ |
| 留在 S2 | 最简单 | S2 也要持有 embedding key 与上游出网权限，S1 仍需同一把 key | ❌ 不推荐（embedding 重建放 S1） |

## 11. P3 落地记录（2026-10-22）

### 11.1 问题

P2 之后数据面可多副本，但**每个副本都跑 30s 定时探活**：3 副本 = 上游被探 3 倍。
控制面虽然是 `mcp.health.enabled=false`，但健康页每次打开都要自己现探一遍，
等于又给上游加了一份压力，而且要求控制面有上游出网权限。

### 11.2 做法

| 组件 | 位置 | 作用 |
|---|---|---|
| `ProbeLeader` + `Memory/RedisProbeLeader` | `health` | Redis 租约 `SET NX PX`，45s TTL；只有一个副本执行定时探测 |
| `ProbeResultCache` + `Memory/RedisProbeResultCache` | `health` | 探测结果写 `mcp:health:probe:{serverId}`（90s TTL），所有副本共读 |
| `HealthQueryPort` | `port`（共享） | 控制面查健康的端口 |
| `HttpHealthQueryPort` | `admin.port` | 控制面走 `/internal/health/**`，不再自己探 |
| `/internal/health/servers[/{id}][/probe]` | 数据面 | 健康数据唯一出口 |

选主规则：

- 租约属于自己 → 续期继续探测；
- 租约空闲 → `SET NX PX` 抢占；
- 租约属于别人 → 跳过定时任务，读共享缓存；
- **Redis 不可用 → 退化为 all-probe**（宁可多打上游，也不要健康数据全空）。

TTL 取值：缓存 90s = 3 × 探测间隔，租约 45s > 间隔 30s。
效果是「leader 挂掉 → 最多 45s 由其它副本接管」，期间读缓存不会立刻变 UNKNOWN。

### 11.3 验证

| 验证 | 结果 |
|---|---|
| 单测 | 218 个全绿（shared 123 / dataplane 63 / admin 32） |
| Redis 契约测试 | 两个 cache 实例互读探测结果；两个 leader 实例只有一个拿到租约；租约过期后另一副本接管 ✅ |
| 双副本实跑 | 1 个 leader + 1 个 follower，Redis 出现 `mcp:health:probe:10` / `:16` ✅ |
| 控制面 | `GET /mcp/admin/health/servers` 返回数据面结果；控制面自身探活次数 0 ✅ |

## 12. P4 落地记录（2026-10-22）

### 12.1 问题

拆分后控制面仍然：

1. 持有 embedding `host/key` 并直连外部向量服务；
2. 在工具增删改、OpenAPI 导入、批量迁移时直接调 `ToolEmbeddingService` 维护索引。

这是典型的「控制面攥着数据面的凭证 + 干了数据面的活」：凭证泄露面变大，
而且控制面需要出网权限。

### 12.2 做法

| 变更 | 内容 |
|---|---|
| 索引维护下沉 | 控制面只发 `TOOL` 事件，带 `toolId` + `op`（`UPSERT` / `DELETE` / `PURGE_SERVER`）；`ConfigChangeApplier` 在数据面增量维护 |
| 重建/状态查询 | `EmbeddingAdminPort` → 数据面 `/internal/embeddings/reindex/{id}`、`/internal/embeddings/stats` |
| 凭证收敛 | `embedding.*` 从共享 profile 移到 `mcp-dataplane/application.yml`；控制面无 host/key，`HttpEmbeddingClient` 恒为 disabled |
| 内部路径隔离 | `McpWebConfig` 把 `/internal/**` 排除在 MCP 鉴权/会话拦截器之外（原来每次内部调用都会多一次 `selectOneByPath` 查询） |

事件粒度：

```text
createTool   → TOOL{serverId, toolId, UPSERT}
updateTool   → TOOL{serverId, toolId, UPSERT}   （换 server 时对原 server 再发 DELETE）
deleteTool   → TOOL{serverId, toolId, DELETE}
deleteServer → TOOL{serverId, op=PURGE_SERVER}
OpenAPI 导入 / 批量迁移 → TOOL{serverId}（无 toolId，数据面整 server 重建）
```

### 12.3 验证

| 验证 | 结果 |
|---|---|
| 单测 | 223 个全绿（shared 123 / dataplane 68 / admin 32） |
| 事件→索引 | 单测覆盖 UPSERT 只索引单个工具、DELETE 只删向量、PURGE_SERVER 清整 server、无 toolId 时整 server 重建 ✅ |
| 控制面代理 | `GET /mcp/admin/embeddings/stats`、`POST /mcp/admin/servers/{id}/embeddings/reindex` 均返回数据面结果 ✅ |
| 控制面无凭据 | 控制面日志无任何 embedding 调用；`embedding.*` 已不在共享 profile 中 ✅ |
| 内部路径 | `/internal/**` 不再触发 MCP 拦截器（dataplane 日志中 `selectOneByPath` 噪声消失）✅ |
