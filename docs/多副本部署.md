# 数据面多副本部署（P2）

> 版本：v1.0 ｜ 日期：2026-10-22 ｜ 适用范围：`mcp-dataplane`（S1）横向扩容
> 前置：已完成服务拆分（见《[服务拆分分析](服务拆分分析.md)》第 9 章）

---

## 1. 结论

数据面可以多副本了，前提是**打开 Redis**：

```bash
MCP_REDIS_ENABLED=true
MCP_REDIS_URL=redis://127.0.0.1:6379/0
```

不开 Redis 也能跑，但**只能单副本**（会话、上游会话、变更事件都在进程内）。

| 能力 | 单副本（默认） | 多副本（Redis） |
|---|---|---|
| MCP 会话 | 进程内 Map | `mcp:session:{id}`，30 min TTL |
| 上游 MCP 会话 | 进程内 Map | `mcp:upstream:{gwSession}`（Hash，field=上游名） |
| 变更事件 | 进程内同步回调 | Pub/Sub `mcp:events:config`，每个副本都收到 |
| 目录缓存 | 进程内 | **仍然是进程内**，靠事件失效 |
| SSE 连接 | 进程内 | **仍然是进程内**，靠事件广播 |
| 超长结果分片 | 内存 | `mcp.tools.chunk-store=redis`（独立开关） |

> SSE 的 `SseEmitter` 是 servlet 对象，**不可能**跨进程共享。
> 正确做法是「事件广播到所有副本，每个副本只推送自己持有的连接」，本实现即如此。
> 代价：客户端必须与某个副本保持长连接（负载均衡默认轮询，SSE 断开重连时会落到任意副本）。

## 2. 扩容

在同一个 Redis 下启动多个 dataplane 实例（各实例用 `MCP_DATAPLANE_PORT` 区分端口），
前置负载均衡把请求分发到任一实例。前提是各副本共享同一 MySQL 与 Redis；
控制面仍建议**单写副本**。

扩容前注意：

- 单副本 JVM 建议 `-Xms384m -Xmx768m`；3.6G 内存的单机建议最多 2 个副本，
  扩容前先看 `free -m` 与进程 RSS，避免 swap/OOM（OOM 可能连带影响 MySQL）；
- 每个实例启动后先做就绪自检（`curl -H "X-Internal-Token: $MCP_INTERNAL_TOKEN" localhost:8081/internal/cluster-info`），
  TCP 端口可连、日志无异常再接流量；
- 数据库增量脚本在扩容前统一执行一次（脚本幂等、可重复执行；建议自行记录已执行的文件）。

## 3. 行为与边界

### 3.1 会话

- `initialize` 在副本 A 建立会话 → 会话写 Redis；
- 后续 `tools/list` 落到副本 B → B 从 Redis 读到同一会话，**不会 401**；
- `DELETE` 终止会话时删 key；TTL 兜底 30 分钟；
- Redis 故障时自动降级为**本副本内存**（日志告警），期间跨副本请求可能 401 —— 这是可接受的降级，不是数据损坏。

### 3.2 变更传播（两条路径）

```
admin ──HTTP /internal/config-changed──▶ dataplane#1
                                            │ PUBLISH mcp:events:config
                        ┌───────────────────┼───────────────────┐
                        ▼                   ▼                   ▼
                  dataplane#1         dataplane#2         dataplane#3
              清资产缓存 +     清资产缓存 +    清资产缓存 +
              广播本机 SSE         广播本机 SSE         广播本机 SSE
```

**兜底**：`RevisionWatcher` 每 30s 比对 `mcp_server` / `mcp_tool` 的「行数 + 最大 update_time」，
发现变化就发一个 `ALL` 事件（清空所有缓存并广播 list_changed）。
这样即使 Redis 丢消息、或控制面根本没连上数据面，缓存也会在 30s 内自愈。

关闭兜底：启动参数 `--mcp.cache.revision-poll-enabled=false`（或环境变量 `MCP_CACHE_REVISION_POLL_ENABLED=false`）。

### 3.3 上游会话

- 网关会话 → 下游 `Mcp-Session-Id` 的映射写 Redis Hash；
- 任一副本可复用同一上游会话，不会因为换副本重新 `initialize`；
- 网关会话终止时整个 Hash 删除。

### 3.4 仍然单点的部分

| 项 | 现状 | 影响 |
|---|---|---|
| 限流/登录失败计数 | 进程内 | 控制面 2 副本时限流阈值变成 2 倍（可接受） |
| 熔断器 | 进程内 | 各副本独立熔断，属预期行为 |

**健康探活已单点化（P3）**：Redis 租约选主，只有一个副本每 30s 探测；
结果写 `mcp:health:probe:{serverId}`（90s TTL）供所有副本与控制面共读。
控制面不再自己探上游，健康页走 `/internal/health/**`。

## 4. 配置项

| 变量 | 默认 | 说明 |
|---|---|---|
| `MCP_REDIS_ENABLED` | `false` | 多副本必须 `true` |
| `MCP_REDIS_URL` | `redis://127.0.0.1:6379/0` | 各副本指向同一个 Redis；兼容旧 `MCP_REDIS_URI` |
| `mcp.redis.key-prefix` | `mcp:` | 多环境共用 Redis 时隔离（启动参数覆盖） |
| `mcp.cache.revision-poll-enabled` | `true` | 变更兜底轮询（环境变量 `MCP_CACHE_REVISION_POLL_ENABLED`） |
| `mcp.cache.revision-poll-ms` | `30000` | 轮询间隔（环境变量 `MCP_CACHE_REVISION_POLL_MS`） |
| `mcp.health.probe-cache-seconds` | `90` | 探测结果缓存 TTL（3 × 探测间隔） |
| `mcp.health.leader-ttl-seconds` | `45` | 选主租约 TTL（> 探测间隔） |

## 5. 自检

数据面暴露内部自检接口（仅回环/内网可访问）：

```bash
curl -s -H "X-Internal-Token: $MCP_INTERNAL_TOKEN" \
  http://127.0.0.1:8081/internal/cluster-info
# {"sessionStore":"redis","eventBus":"redis","redisEnabled":true,"keyPrefix":"mcp:","redisReachable":true,"probeLeader":true}
```

判定标准：

- `redisReachable=false` → Redis 连不上，会话/事件会降级为本地，**不要扩容**；
- `sessionStore=memory` 或 `eventBus=local` → `MCP_REDIS_ENABLED` 没打开；
- `probeLeader=true` 的副本只有一个（多副本时），它负责 30s 定时探活。

> Redis 掉线不会让服务启动失败：变更事件会退化为本地分发（当前副本仍然正确），
> 会话退化为本副本内存（跨副本请求可能 401）。这是刻意设计的降级，不是故障扩散。

Redis 侧可以确认订阅数：

```bash
redis-cli pubsub numsub mcp:events:config
# 1) "mcp:events:config"
# 2) (integer) 3        <- 三个数据面副本
```

## 6. 灰度顺序

1. 单副本 + `MCP_REDIS_ENABLED=true`，跑一轮冒烟（`/internal/cluster-info` 应为 redis）；
2. 扩到 2 副本，观察 401/会话丢失；
3. 观察上游 QPS 与探活日志（应只有一个副本实际探活，其余副本读共享结果）；
4. 再扩到 3+。
