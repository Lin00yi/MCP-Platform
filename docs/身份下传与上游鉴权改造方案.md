# MCP 身份下传与上游鉴权改造方案（方案 A：JWE + JWS）

> **2026-10 认证变更**：网关只认 `x-dsh-auth-token`；用户信息服务（userinfo）与 pass-through 相关配置已删除，`MCP_IDENTITY_*` 仅保留下游内部断言用途。本文的用户信息服务段落实为历史设计。


> 版本：v1.0 · 2026-10
> 目标：外部应用 token → 网关验签 → 用户信息补全 → 短时内部 JWT（JWE）→ 自研 MCP Server 验签
> 方案 C（OAuth2 Token Exchange）暂不实施，列入《待办清单》。

---

## 1. 结论与边界

本方案采用 **Trusted Gateway + 短时内部身份断言**：

1. 网关校验外部 `access-token`（应用 JWT），得到 `appId`；
2. 网关用应用侧传递的 **用户 token** 调用用户信息服务，换取 `userId / customerId / scopes`；
3. 网关完成 `app → server/tool` 授权；**客编完全由用户信息服务返回，客户端不传客编**；租户由 `appId` 的归属决定，不由用户服务返回；
4. 网关签发 **60 秒有效、按下游 audience 限定、JWE 加密** 的内部身份断言；
5. 下游 MCP Server 解密/验签后得到 `app / user / tenant / customer`，**只按断言中的客编做数据隔离**，不信任请求参数里的客编；
6. 原始应用 token、用户 token **不向下游透传**。

不在本方案范围：
- 下游再调用其他业务系统的令牌交换（方案 C，待办）；
- 网关到下游的 mTLS/服务网格（当前没有，用 JWE + 网络收敛补偿）；
- 多实例 Redis 化（另行排期）。

## 2. 身份模型

| 概念 | 说明 | 来源 |
|---|---|---|
| App | 接入应用（MCP 客户端） | `access-token.iss` + `enn_app_info.app_secret` 验签 |
| Tenant | 当前调用的 MCP Server 所属业务方 | **`mcp_server.tenant_id`**（应用为全局资源，不再绑定租户） |
| User | 应用侧真实用户 | 用户信息服务（用 `x-dsh-auth-token` 换取） |
| Customer（客编） | 用户的数据范围标记，**一个用户可多个，但一次请求只有一个当前客编** | 用户信息服务返回的 **单个当前客编** `customerId`（由用户 token 上下文决定） |

关键约束：

- **App 与 Customer 不是一对一**。App 归属一个 Tenant；一个 User 可拥有多个 Customer。
- 运行时数据范围由 **User + Customer** 决定，不由 App 决定。
- **客户端不传客编**。客编由用户信息服务根据 `x-dsh-auth-token` 的上下文返回单个 `customerId`（通常 token 已绑定当前客编）；网关只做信任传递。
- **用户服务不返回 tenantIds**。Tenant 是后台业务方概念，取当前调用的 MCP Server 的 `tenant_id`；应用本身不绑定租户。
- **appId 由客户端 `access-token` 提供**，网关用 `app_secret` 验签；用户服务只负责用户/客编，不负责应用身份。
- **`access-token` 不是裸 appId**：它是 `iss=appId` 的 HS256 JWT，已签名且带 `exp`；传输层用 HTTPS 即可，不需要再加密。不要把裸 appId 当凭证（知道 appId 即可冒充）。
- 客编是敏感数据：不落日志、不放 URL、不在错误信息中回显；内部断言中加密传输。
- 网关未来可能并入用户信息服务，因此用户信息获取必须通过接口抽象，不能写死 HTTP 调用。

## 3. 总体流程

```
Client                Gateway                         UserInfo Service        MCP Server
  |                      |                                  |                     |
  |-- access-token ----->|                                  |                     |
  |   x-dsh-auth-token ->|                                  |                     |
  |                      |-- 验签 app token --------------->|                     |
  |                      |-- 查 app_server_rel / app_tool_rel                     |
  |                      |-- 用 user token 查用户信息 ------>|                     |
  |                      |<-- userId/customerId -----------|                     |
  |                      |-- 校验 tenant / app 归属                               |
  |                      |-- 签发 60s JWE 内部断言                                |
  |                      |---------------- Authorization: Bearer <JWE> ---------->|
  |                      |                                  |   解密 + 验签 + 客编隔离
  |                      |<----------------- JSON-RPC result --------------------|
  |<-- JSON-RPC result --|                                  |                     |
```

### 3.1 请求头约定

| 头 | 必填 | 说明 |
|---|---|---|
| `access-token` | 是 | 应用 JWT（现有），`iss=appId`，HS256 用 app_secret 验签 |
| `x-dsh-auth-token` | 是（initialize + 受保护方法） | 应用侧用户 token（DSH 客户端的 token key），仅用于网关调用用户信息服务，不透传下游 |
| `Mcp-Session-Id` | initialize 后必填 | 现有 Streamable HTTP 会话 |

> **客户端不传客编**。客编由用户信息服务根据 `x-dsh-auth-token` 返回；如果用户有多个客编，应由应用侧在签发用户 token 时确定“当前客编”（customer-scoped token），而不是让客户端在 MCP 请求里自报。
>

> 为什么用户 token 不用 `Authorization`：标准 MCP 客户端（Codex 等）会把应用 JWT 放在 `Authorization: Bearer`，同时 `SK_EXCHANGE` 也使用 `Authorization`。使用 `x-dsh-auth-token` 可避免歧义，并与 DSH 客户端的 token key 保持一致。

### 3.2 公开方法

- `initialize`：**需要** `access-token` + `x-dsh-auth-token`；网关用 appId 反查归属租户，调用用户信息服务取得当前客编，并绑定会话；
- `ping`、`notifications/*`：公开；
- 其余方法：需要完整身份上下文。

> 当前实现按 `mcp.identity.enabled=true` 全量强制；`OPTIONAL` 灰度（只记录不阻断）尚未实现。

### 3.3 pass-through 模式（不换用户信息）

如果暂时没有用户信息服务，可开启身份校验但**不换取用户信息**：

```yaml
mcp:
  identity:
    enabled: true
    resolve-userinfo: false       # 不调用 userinfo
    forward-user-token: true      # 原样透传 x-dsh-auth-token
    token-format: JWS             # 网关只签名来源断言，不需要下游 JWE 公钥
```

行为：

1. 网关要求 `x-dsh-auth-token`，缺失返回 401；
2. 只把 token 的 SHA-256 绑定到 `Mcp-Session-Id`，防止同一会话中途换 token；
3. 不解析 `userId/customerId`，日志“用户”为空，也不覆盖客编参数；
4. 转发下游时带两个头：
   - `Authorization: Bearer <网关 JWS>`：证明请求来自网关；
   - `x-dsh-auth-token: <原始用户 token>`：由下游自行校验用户身份；
5. 下游用网关公钥验 `Authorization`，校验 `iss=mcp-gateway`、`aud=<server audience>`、`exp/iat/jti`。

下游验签参考实现：[`GatewayOriginVerifier`](../mcp-gateway/src/main/java/com/mcp/transfer/identity/verifier/GatewayOriginVerifier.java)。

> 网关签名私钥必须固定配置（`MCP_IDENTITY_SIGNING_KEY`）；否则每次重启生成临时密钥，下游无法验签。
> 用户 token 不落日志、不落库，只在进程内传递。

## 4. 接口契约

### 4.1 用户信息服务（Gateway → UserInfo）

```http
GET /internal/userinfo
Authorization: Bearer <x-dsh-auth-token 的值>
X-MCP-App-Id: <appId>
```

响应：

```json
{
  "code": 0,
  "data": {
    "userId": "u-123",
    "userName": "张三",
    "customerId": "CUST-001",
    "scopes": ["tool:add", "tool:echo"],
    "expiresAt": 1780000000
  }
}
```

错误约定：

| 场景 | HTTP | code | 网关行为 |
|---|---|---|---|
| token 无效/过期 | 401 | 401 | 返回 MCP `-32001` |
| 用户无任何客编 / 未返回当前客编 | 200 | 0 但 `customerId` 为空 | 返回 `-32003`（用户服务必须返回单个当前客编） |
| Server 未配置租户 | - | - | 返回 `-32003`（无法确定业务方） |
| 用户服务不可用/超时 | 5xx/超时 | - | **fail closed**，返回 `-32603` / HTTP 503 |


实现建议：

- 超时 1.5s，重试 0 次（快速失败）；
- 本地缓存 30s，key = `SHA-256(userToken + "|" + appId)`，**不缓存原始 token**；
- 用户服务返回 401 时立即清除缓存；
- 预留 `UserInfoClient` 接口：
  ```java
  public interface UserInfoClient {
      UserIdentity resolve(String appId, String userToken);
  }
  ```
  未来网关并入用户服务时，替换为 `LocalUserInfoClient`，不改编排层。
- `customerId` 是**必须字段（单值）**：它代表当前用户 token 所绑定的客编上下文；不返回 `customers` 列表，也不允许客户端选择。

### 4.2 内部身份断言（Gateway → MCP Server）

**格式：JWE（RSA-OAEP-256 + A256GCM）包裹 JWS（RS256）**，放在 `Authorization: Bearer <JWE>`。

外层 JWE Header：

```json
{ "alg": "RSA-OAEP-256", "enc": "A256GCM", "cty": "JWT", "kid": "<downstream-key-id>" }
```

内层 JWS Claims：

| Claim | 说明 |
|---|---|
| `iss` | `mcp-gateway` |
| `aud` | 下游 audience（每个 MCP Server/Upstream 一个） |
| `sub` | `appId:userId` |
| `app` | appId |
| `uid` | userId |
| `tid` | tenantId |
| `cust` | 客编（敏感，JWE 加密后不可读） |
| `scope` | 允许的 tool 列表（可选） |
| `srv` | serverId |
| `trace` | traceId |
| `iat` / `exp` | 签发/过期，TTL 60s |
| `jti` | 随机 UUID，用于防重放 |

示例明文（仅内层，实际被 JWE 加密）：

```json
{
  "iss": "mcp-gateway",
  "aud": "pcb-server",
  "sub": "JLC-Work:u-123",
  "app": "JLC-Work",
  "uid": "u-123",
  "tid": 5,
  "cust": "CUST-001",
  "scope": ["tool:add"],
  "srv": 10,
  "trace": "3da7f0d1...",
  "iat": 1780000000,
  "exp": 1780000060,
  "jti": "9f2c..."
}
```

> 如果下游暂时不支持 JWE，可降级为 JWS + **强制内网 HTTPS**，配置 `mcp.identity.token-format=JWS`。客编敏感场景不建议长期使用 JWS 明文。

### 4.3 下游验签规则

1. 从 `Authorization: Bearer` 取 JWE；
2. 用自己的私钥解密（`kid` 匹配）；
3. 用网关公钥/JWKS 验内层 JWS（`kid` 匹配）；
4. 校验 `iss=mcp-gateway`、`aud=自己的 audience`、`iat/exp`（允许 30s 时钟偏移）、`jti` 未重放；
5. 写入 `McpIdentityContext`：
   ```java
   appId, userId, tenantId, customerId, scopes, traceId, jti
   ```
6. 业务层**只使用 `customerId`**，禁止从请求参数/请求头再次读取客编；
7. 失败返回 401，`WWW-Authenticate: Bearer error="invalid_token"`。

重放缓存：`jti` 缓存 2×TTL（约 2 分钟），本地 Caffeine 即可；多实例时换 Redis。

### 4.4 错误码

| 场景 | JSON-RPC code | HTTP |
|---|---|---|
| 缺应用 token / 验签失败 | -32001 | 400 |
| 缺用户 token / 用户 token 无效 | -32001 | 400 |
| 用户无客编 / 未返回当前客编 | -32003 | 400 |
| app 未配置归属租户 | -32003 | 400 |
| 会话已绑定客编，但用户服务返回不同客编 | -32602 | 400 |
| 用户信息服务不可用 | -32603 | 503 |
| 下游断言无效/过期 | -32001 | 401 |

## 5. 数据模型与迁移

### 5.1 应用归属

```sql
CREATE TABLE mcp_app_owner (
  app_id      VARCHAR(128) NOT NULL PRIMARY KEY,
  tenant_id   INT NOT NULL,
  created_by  BIGINT,
  create_time DATETIME,
  update_time DATETIME,
  KEY idx_tenant (tenant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

回填（按已有授权推导）：

```sql
INSERT INTO mcp_app_owner (app_id, tenant_id, create_time, update_time)
SELECT r.app_id, MIN(s.tenant_id), NOW(), NOW()
FROM app_server_rel r
JOIN mcp_server s ON s.id = r.server_id
GROUP BY r.app_id;

-- 冲突检查：一个 app 授权到多个租户
SELECT r.app_id, GROUP_CONCAT(DISTINCT s.tenant_id)
FROM app_server_rel r JOIN mcp_server s ON s.id = r.server_id
GROUP BY r.app_id
HAVING COUNT(DISTINCT s.tenant_id) > 1;
```

> 冲突 app 需人工确认归属；未回填的 app 只允许超管管理。

### 5.2 下游 audience 与 upstream 配置

```sql
ALTER TABLE mcp_server
  ADD COLUMN audience VARCHAR(128) COMMENT '内部 JWT aud，默认 server-{id}',
  ADD COLUMN identity_mode VARCHAR(16) DEFAULT 'OPTIONAL' COMMENT 'OFF/OPTIONAL/REQUIRED';

CREATE TABLE mcp_upstream (
  id BIGINT NOT NULL AUTO_INCREMENT,
  server_id INT NOT NULL,
  name VARCHAR(64) NOT NULL,
  url VARCHAR(500) NOT NULL,
  auth_type VARCHAR(32) DEFAULT 'GATEWAY_JWE'
      COMMENT 'GATEWAY_JWE/GATEWAY_JWS/BEARER/API_KEY/NONE',
  audience VARCHAR(128),
  encryption_public_key LONGTEXT COMMENT '下游 JWE 公钥（PEM/JWK）',
  auth_config LONGTEXT COMMENT '静态凭证，加密存储',
  status TINYINT DEFAULT 1,
  create_time DATETIME,
  update_time DATETIME,
  PRIMARY KEY (id),
  UNIQUE KEY uk_server_name (server_id, name),
  KEY idx_server (server_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

迁移：把 `mcp_server.upstream_url` 的 JSON 数组解析成 `mcp_upstream` 行；单 MCP 使用 `name='default'`。过渡期保留 `upstream_url`，读路径优先 `mcp_upstream`。

### 5.3 配置示例

```yaml
mcp:
  identity:
    enabled: true
    mode: OPTIONAL            # OFF/OPTIONAL/REQUIRED
    token-format: JWE         # JWE/JWS
    issuer: mcp-gateway
    signing-private-key: ${MCP_IDENTITY_SIGNING_KEY}
    signing-kid: gw-2026-10
    jwks-url: https://gateway.internal/.well-known/mcp-gateway-jwks.json
    user-token-header: x-dsh-auth-token
    resolve-userinfo: true     # false=pass-through，不调用户服务
    forward-user-token: true   # 是否把原始用户 token 透传下游
    userinfo-url: http://userinfo.internal/internal/userinfo
    userinfo-timeout-ms: 1500
    cache-ttl-seconds: 30
```

## 6. 后端改造点

| 文件/类 | 改造 |
|---|---|
| `McpAuthInterceptor` | 验应用 token 后，取用户 token 调 `UserInfoClient`；校验 tenant/customer；把 `userId/tenantId/customerId/scopes` 写 request attribute |
| `McpAuthService` | 保持 app 验签；新增 `checkAppTenant(appId, tenantId)`（可选） |
| 新增 `UserInfoClient` / `HttpUserInfoClient` | 用户信息换取 + 缓存 + fail closed |
| 新增 `UserIdentity` DTO | userId / customerId / scopes（单客编） |
| 新增 `IdentityResolver` | 组合 app + userinfo + customer 选择，输出 `ResolvedIdentity` |
| 新增 `InternalIdentityTokenService` | 生成 JWE（内层 JWS），按 `aud`/`kid` 签发 |
| 新增 `McpIdentityContext`（下游侧） | ThreadLocal 身份上下文 |
| `McpSessionCache` | value 从 `Long` 改为 `SessionInfo`（expireAt + identity），initialize 后绑定 |
| `McpServiceImpl.handleMcpRequest` | initialize 时绑定 identity；tools/call 前校验会话客编 |
| `McpUpstreamClient.forwardRaw/doInitialize/ensureSession` | 加 `Authorization: Bearer <JWE>`；保留 `Mcp-Session-Id` |
| `McpServerHealthProbe` | 探活也带内部断言（或单独的探活 token） |
| `McpAdminController` | 应用归属过滤/校验；server audience/identity_mode；upstream 编辑与密钥配置 |
| `McpAdminDiscoveryController` | 不受影响（admin JWT） |
| `McpServer` / 新增 `McpUpstream` | 实体、Mapper、XML、迁移 |
| `McpAppOwner` | 实体、Mapper、XML |

### 6.1 用户 token 与客编选择流程

```java
// 伪代码
AppIdentity app = verifyAppToken(accessToken);          // appId 由客户端 access-token 提供
UserIdentity user = userInfoClient.resolve(app.appId(), userToken);

// 租户来自 app 归属，不来自用户服务
Integer tenantId = app.ownerTenantId();
if (tenantId == null) throw FORBIDDEN;                  // app 未配置业务方

// 客编来自用户信息服务，单值，客户端不参与选择
String customerId = user.customerId();
if (customerId == null || customerId.isBlank()) throw FORBIDDEN;

ResolvedIdentity identity = new ResolvedIdentity(app, user, tenantId, customerId);
request.setAttribute(MCP_IDENTITY_ATTR, identity);
```

### 6.2 会话绑定

- `initialize`：网关生成 `Mcp-Session-Id` 后，把 `appId/userId/tenantId/customerId` 写入 `SessionInfo`；其中 `tenantId` 来自 `mcp_app_owner`，`customerId` 来自用户服务；
- 后续请求：`McpAuthInterceptor` 重新调用用户信息服务（可命中 30s 缓存），比对 session 中的 `appId/userId/customerId`；
- 不一致：`-32602`，防止同一 session 切换客编；用户切换客编应重新走应用侧登录/换 token。
- **租户校验**：默认要求 `app.ownerTenantId == server.tenantId`；跨租户授权需单独开关/审批，本期默认拒绝。

### 6.3 客编覆盖

- 下游必须只信任 JWT 中的 `cust`；
- 客户端不允许通过 `X-MCP-Customer-Id` 或工具参数指定客编；
- 网关对 `tools/call` 参数中的 `customerId` / `customer_id` / `custId` 做**覆盖**（配置化字段名），统一替换为用户信息服务返回的客编，避免模型传入其他客编；
- 未在配置中的字段不处理，由下游自行忽略。

### 6.4 REST 工具（外部 HTTP API）

`McpServiceImpl.callExternalService` 当前只透传 `agentChannel`。对于外部 HTTP API：

- 默认**不透传内部 JWT**（避免把网关签名密钥暴露给公网服务）；
- 如需客编上下文，由**网关向目标 API 注入** `X-MCP-Customer-Id` / `X-MCP-User-Id` 头（不是客户端传入），并要求目标 API 在内网/可信网络；更稳妥的方式是方案 C 的 token exchange；
- 外部 API 的鉴权仍走现有 `SK_EXCHANGE/API_KEY/BEARER`。

## 7. 下游接入规范（自研 MCP Server）

建议提供一个可复用的 Spring Boot Starter / Filter：

```java
@Configuration
public class McpIdentityAutoConfiguration {
    @Bean
    public Filter mcpIdentityFilter(...) { ... }
}
```

Filter 逻辑：

1. 放行健康检查等白名单路径；
2. 取 `Authorization: Bearer`；
3. JWE 解密（私钥）；
4. JWS 验签（网关公钥/JWKS）；
5. 校验 `iss/aud/exp/iat/jti`；
6. 设置 `McpIdentityContext`；
7. `finally` 清理 ThreadLocal。

配置：

```yaml
mcp:
  identity:
    enabled: true
    issuer: mcp-gateway
    audience: pcb-server
    gateway-jwks-url: http://gateway.internal/.well-known/mcp-gateway-jwks.json
    decryption-private-key: ${MCP_DOWNSTREAM_JWE_PRIVATE_KEY}
    decryption-kid: pcb-2026-10
    clock-skew-seconds: 30
    replay-cache-ttl-seconds: 120
```

业务代码：

```java
String customerId = McpIdentityContext.current().customerId();
// 所有查询强制 where customer_id = ?
```

要求：
- 禁止从 request header/body 读取客编；
- 日志中客编脱敏（只打印 hash 或后 4 位）；
- 未通过验签的请求直接 401，不进入业务；
- 下游只监听内网，安全组只放行网关出口 IP。

## 8. 无 mTLS / 无网络策略下的补偿

| 风险 | 补偿 |
|---|---|
| 伪造身份 | JWE + JWS 双层，私钥不下发下游 |
| 窃听 | JWE 加密客编；仍建议内网 HTTPS |
| 重放 | 60s TTL + `jti` 缓存 + `aud` 限定 |
| 横向访问 | 下游安全组只放行网关 IP；网关出网 allowlist |
| 网关被 SSRF | 上游 host/port 白名单 + 连接层 DNS 校验 + 禁止重定向 |
| 密钥泄露 | 非对称密钥、`kid` 轮换、私钥放 KMS/环境变量 |
| 客编落日志 | 全局脱敏；审计只存 `cust_hash` |

> 即使没有 mTLS，JWE 也能保证“只有目标下游能解密、只有网关能签发”。但**网络收敛仍然必须做**，否则任何内网服务都能尝试重放/探测。

## 9. 分阶段实施

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| 0 | 确认契约：userinfo 响应、JWE/JWS、客编来源、密钥管理 | 1–2 天 | 文档评审通过 |
| 1 | `mcp_app_owner` + 管理端过滤/校验 + 回填 | 1.5–2 天 | 租户只能看/管自己的 app |
| 2 | `UserInfoClient` + `IdentityResolver` + 缓存 + 脱敏 | 2 天 | 用户信息换取、失败 fail closed |
| 3 | 内部 JWE 签发 + 下游 Filter + 健康探活 | 2–3 天 | 下游能验签并拿到客编 |
| 4 | 客编传递 + 会话绑定 + 参数覆盖 | 1–2 天 | 多客编/切换/越权用例通过 |
| 5 | SSRF allowlist + cookie/CSP（独立项） | 3 天 | 见对应方案 |

每阶段用 `mcp.identity.mode=OPTIONAL` 灰度，观察日志后再切 `REQUIRED`。

## 10. 测试矩阵

- 应用 token：缺失/过期/错误签名/正确；
- 用户 token：缺失/过期/用户服务 401/5xx/超时；
- 租户：app 无 owner tenant → 403；app owner tenant 与 server tenant 不一致 → 403（默认）；
- 客编：服务返回单个当前客编 / 未返回；客户端无法通过 header 或参数覆盖；
- 会话：initialize 绑定 C1，后续切 C2 → 409；换 app/user → 403；
- 内部 JWT：过期/错误 aud/错误 kid/篡改/重放；
- 下游：未带断言 401；断言合法 200；客编隔离查询正确；
- 日志：token、客编不出现在日志/错误响应；
- 管理端：租户 app 隔离、跨租户授权拒绝；
- SSRF：allowlist、DNS rebinding、重定向。

## 13. 下游接入示例（Nimbus JOSE + JWT）

```xml
<dependency>
  <groupId>com.nimbusds</groupId>
  <artifactId>nimbus-jose-jwt</artifactId>
  <version>9.37.3</version>
</dependency>
<!-- PEM 解析需要 -->
<dependency>
  <groupId>org.bouncycastle</groupId>
  <artifactId>bcpkix-jdk15on</artifactId>
  <version>1.70</version>
</dependency>
```

```java
McpIdentityVerifier verifier = new McpIdentityVerifier(
    gatewayPublicKeyPem,
    downstreamPrivateKeyPem,
    "mcp-gateway",
    "pcb-server");

VerifiedIdentity identity = verifier.verify(request.getHeader("Authorization"));
String customerId = identity.getCustomerId(); // 业务查询必须使用该值
```

> 网关侧可直接参考 `com.mcp.transfer.identity.verifier.McpIdentityVerifier` 的实现。

## 14. 需要确认的决策点

1. 用户 token 头已统一为 `x-dsh-auth-token`（与 DSH 客户端一致，避免与标准 MCP 的 `Authorization` 冲突）。
2. 内部断言默认 **JWE** 是否可接受？下游是否能引入 Nimbus JOSE + JWT 依赖？
3. 用户信息服务能否稳定返回**单个当前客编** `customerId`（由用户 token 绑定）？切换客编是否重新签发用户 token？
4. `appId` 确认由客户端 `access-token` 提供；用户服务不再返回 appId/tenantIds，是否确认？
5. app 归属租户与 server 归属租户不一致时，是否一律拒绝（跨租户授权需单独开关）？
