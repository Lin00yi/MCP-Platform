# 工具规模治理（白名单 / 分页 / META 元工具）

> 适用版本：2026-10 起
> 关联代码：`com.mcp.transfer.exposure.*`、`McpServiceImpl#buildToolListResult`、`McpDiscoveryService`
> 关联迁移：`db/mysql/migrations/20261018_tool_exposure.sql`

---

## 1. 问题：工具定义会占满上下文

MCP 客户端在会话建立时调用 `tools/list`，随后把**工具定义**放进每一轮模型请求。
工具定义不是免费的：

| 场景 | 约消耗 |
|---|---|
| GitHub 35 个工具 | 26K tokens |
| 5 个 server / 58 个工具 | 55K tokens |
| 1,000 个工具（按 300–700/个） | 0.3M–0.7M tokens |
| 3,000 个工具 | 1M–2M tokens，直接超窗 |

除了成本，工具越多**选错工具/传错参数**的概率也越高。所以网关必须在“谁能看到哪些工具”和“一次返回多少”两层做治理，而不是让客户端把全量拉下来。

> `tools/list` 的分页（`cursor`/`nextCursor`）只解决“响应太大传不动”，不解决“该给模型看哪些”。真正的减量靠**访问模式**和**暴露模式**。

---

## 2. 三种访问模式（谁能看到）

`mcp_server.tool_access_mode`：

| 值 | 语义 | 适用 |
|---|---|---|
| `WHITELIST` | 只返回 `app_tool_rel` 显式授权的工具；未配置 = 看不到 | **默认**，推荐 |
| `ALL` | 返回 Server 下全部启用工具（忽略细粒度授权） | 内部可信应用、工具少 |

> 访问模式只有 `WHITELIST` / `ALL` 两种；Prompt 与 Resource 使用同一套枚举，在 Server 上分别独立配置。

关键点：

- **数据面 `tools/list` 与 `tools/call` 使用同一套规则**。修复了旧版本“列表已过滤、但按名字仍能调用”的漏洞。
- 管理台以“最坏情况”（未指定应用时按全量）估算预算并告警。
- Server 级授权在白名单模式下会自动写入**当前全部工具**的细粒度授权，保持“勾选 Server 即获得全部资产”的既有交互；之后新增的工具需要再次授权。

## 3. 两种暴露模式（一次返回多少）

`mcp_server.tool_exposure_mode`：

### 3.1 DIRECT（默认）

`tools/list` 返回全部可见工具，超过 `mcp.tools.page-size`（默认 200）时按 `mcp_tool.id` 游标分页：

```json
// 请求
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{"cursor":"djE6MjAw"}}
// 响应
{"result":{"tools":[...],"nextCursor":"djE6NDAw","_meta":{...}}}
```

- `cursor` 对客户端不透明；非法 cursor 按第一页处理。
- **不是所有客户端都会跟随 `nextCursor`**。因此默认页大小给到 200，只在超过时才分页；接入前请确认客户端支持分页。
- `_meta` 是网关扩展字段，客户端可忽略：`totalTools/visibleTools/returned/accessMode/exposureMode/hotTools/warnThreshold/maxThreshold/overWarn/overMax/estimatedTokens`。

### 3.2 META（元工具 + 热工具）

`tools/list` 只返回：

1. 配置的**热工具**（`mcp_server.hot_tool_codes`，最多 50 个，带完整 `inputSchema`）；
2. 四个固定元工具：
   - `search_tools`：检索或按业务分组列目录，只返回 `name/description/tags`；
   - `get_tool_schema`：按需展开 `inputSchema`（支持批量与 compact/full）；
   - `call_tool`：按工具名执行，复用标准 `tools/call` 的鉴权、参数校验、日志；
   - `read_result_chunk`：分段读取被截断的超长结果（替代 `Resources`）。

典型调用链：

```json
// 1) 检索（query 留空 = 按业务分组列目录）
{"method":"tools/call","params":{"name":"search_tools","arguments":{"query":"订单 退款","top_k":10}}}

// 2) 看参数
{"method":"tools/call","params":{"name":"get_tool_schema","arguments":{"name":"refund_apply"}}}

// 3) 执行（reason 用于审批展示与审计）
{"method":"tools/call","params":{"name":"call_tool","arguments":{"name":"refund_apply","arguments":{"orderNo":"A1"},"reason":"用户申请退款"}}}

// 4) 结果超长时按 call_id 分段读取
{"method":"tools/call","params":{"name":"read_result_chunk","arguments":{"call_id":"...","offset":4000,"limit":3000}}}
```

注意事项：

- `search_tools` 的检索范围 = 当前应用可见工具（白名单生效），不会越权返回。
- `call_tool` 会拒绝调用元工具本身（防递归），并重新校验目标工具是否可见。
- 未配置热工具时，所有工具都需要先 `search_tools`，会多一轮推理；建议保留 5–20 个高频工具。
- 工具级错误（未授权、参数不合法、目标不存在）以 `isError: true` 的 content 返回，模型可以读取并修正。
- `search_tools` / `get_tool_schema` / `call_tool` / `read_result_chunk` 是保留工具名，真实工具不能再使用（创建/更新时会校验）。

### 3.3 统一入口（Endpoint）的 META 合并

客户端只通过 `/mcp/e/{endpointKey}` 接入，因此暴露策略必须在**聚合层**生效，否则 META 配置不会影响真实链路。

`McpAggregateService` 按成员 Server 各自的 `tool_exposure_mode` 合并：

| 成员 Server 模式 | 贡献到 Endpoint `tools/list` 的内容 |
|---|---|
| `DIRECT` | 该 Server 全部可见工具（工具名加 namespace 前缀） |
| `META` | 仅 `hot_tool_codes` 中的常驻热工具（加前缀） |
| 任一 `META` 存在 | 额外追加**一套端点级** `search_tools / get_tool_schema / call_tool / read_result_chunk` |

要点：

- 元工具**不带 namespace 前缀**，检索与代理范围覆盖整个 Endpoint（跨 namespace / 跨 Server）；
- 元工具只在“至少一个成员 Server 为 META”时出现；只有 DIRECT Server 的 Endpoint 行为与旧版一致；
- `MCP_TOOLS_META_ENABLED=false` 时全部按 DIRECT 处理，作为应急回退；
- `search_tools` 返回的 `name` 是**带前缀的暴露名**，`server` 字段标明所属 namespace，供模型消歧；
- `get_tool_schema` / `call_tool` 接受暴露名，网关内部解包前缀，再复用标准鉴权与参数校验；
- `tools/list` 的 `_meta` 增加：`exposureMode`（META/DIRECT）、`directServers`、`metaServers`、`hotTools`、`visibleTokens`、`returnedTokens`、`tokenizer`。

### 3.4 超长工具名（64 字符）

`{namespacePrefix}__{toolCode}` 可能超过模型接口限制，DSH 等客户端还会再叠加 `mcp__{serverName}__`。
网关在暴露时统一走 `AggregateNaming.exposeTool`：

- 未超限：保持 `{prefix}__{code}`；
- 超限：保留前缀 + 可读前段，追加 `_{8位短哈希}`，总长 ≤ `mcp.tools.max-exposed-name-length`（默认 64）；
- 调用时先按 code 精确查，查不到再按“暴露名反查”定位真实工具（代理 Server 同理），因此别名对客户端完全透明。

> namespace 前缀本身最长 32，加上分隔符与 8 位哈希后仍有足够的可读 code 空间；哈希由工具名确定性生成，重启/多副本一致。


### 3.5 `search_tools` 检索策略

由 `mcp.tools.search-mode` 配置，默认 `AUTO`：

| 模式 | 行为 | 适用 |
|---|---|---|
| `AUTO`（默认） | query 为空 → `CATALOG`；否则有 embedding 用 `HYBRID`，没有用 `BM25` | 大多数场景 |
| `CATALOG` | 不打分：无 `domain` 时返回分组概览（domain / server / toolCount），指定 `domain` 时列出该组工具摘要 | 工具 15~50 个 |
| `KEYWORD` | 字段加权关键词匹配（零依赖） | 精确英文缩写、接口编码 |
| `BM25` | 标准 BM25（ASCII 词 + CJK 单字/二元组） | 无向量服务时的默认 |
| `VECTOR` | 余弦语义检索（不可用时自动降级 BM25） | 口语提问 |
| `HYBRID` | BM25 + 向量，RRF（k=60）融合 | 数百~上千工具 |

参数：`query?`、`domain?`、`tags?`、`server_id?`、`top_k?`（兼容旧 `tag` / `limit`）。
返回值带 `mode`，便于观察实际生效的策略；`search_tools` 不返回 `inputSchema`。

### 3.6 超长结果截断与分片读取

工具结果超过 `mcp.tools.result-spill-threshold`（默认 4000 字符）时：

1. 全文写入进程内暂存区（LRU + TTL，按 appId 隔离），返回短 `call_id`；
2. 本次只返回前 4000 字符 + 总长度 + 下一步调用指引；
3. `read_result_chunk(call_id, offset, limit)` 按偏移继续读取，默认 3000 字符。

说明：

- 只在 META 模式启用（DIRECT 模式没有 `read_result_chunk`，仍走 1MB 硬截断）；
- 单条暂存上限 `result-spill-max-chars`（默认 4M 字符），防止内存被打爆；
- `mcp.tools.chunk-store=memory`（默认）为进程内 LRU；
  `=redis` 时同时写入 Redis（`mcp.tools.redis-uri`），支持多副本跨节点读取；
- Redis 不可用时自动回退进程内缓存，30 秒冷却后重试，不影响工具调用。
- 本地已验证（2026-10-20）：`chunk-store=redis` + DB9，写入 `mcp:chunk:{callId}`、
  TTL 1800s，`read_result_chunk` 可正常分段返回。

### 3.7 双版本 Schema 与离线元数据增强

**双版本 Schema（E2）**：

- `get_tool_schema` 支持 `tool_codes` 批量（最多 10 个）与 `detail_level`：
  - `compact`（默认）：保留 type/properties/required/enum/items/oneOf 等填参关键字，
    剔除 description/title/default/examples/$schema 等展示字段；
  - `full`：返回入库完整 Schema，便于排障；
- 响应带 `tokens`，可直接观察单个/批量 Schema 的上下文成本；
- 参数校验始终使用完整 Schema，不受 `compact` 影响。

**离线元数据增强（E1 基线）**：

- `ToolMetadataEnricher` 在检索前对 code/name 做 snake_case / camelCase 拆词，
  并通过 `ToolSynonyms` 反向补中文（`order_query` → order、query、订单、查询）；
- 补出的词并入 description 与 tags，参与 BM25/关键词/向量检索；
- 零外部依赖、幂等、不落库；`MCP_TOOLS_METADATA_ENRICH=false` 可关闭；
- 后续接入 LLM 离线增强时，只需替换 `ToolMetadataEnricher#generatedTerms`。

### 3.8 下游熔断（E5）

`UpstreamCircuitBreaker` 保护真实调用链，与健康探测互补：

- 同一 Server 连续失败达到 `mcp.health.circuit.failure-threshold`（默认 5）→ 打开；
- 打开后 `mcp.health.circuit.open-seconds`（默认 30 秒）内直接返回
  `isError=true` 的“已熔断”提示，不再等待下游超时；
- 到期放行一次探测：成功关闭，失败重新打开；
- 状态按 Server、进程内维护，多副本各自独立。

覆盖：本地/HTTP 工具执行（`McpServiceImpl`）与 MCP 上游代理（`McpUpstreamClient`）。
参数校验失败**不计入**熔断失败，避免模型填错参数误伤下游。

## 4. 预算告警

| 项 | 默认 | 说明 |
|---|---|---|
| `mcp.tools.warn-threshold` | 100 | 可见工具数超过即 WARN 日志 + 管理台告警 |
| `mcp.tools.max-threshold` | 500 | 超过即 ERROR 日志 + 管理台高亮（不阻断调用） |
| `mcp.tools.warn-throttle-seconds` | 600 | 同一 Server 同类告警节流 |

Server 可通过 `tool_warn_threshold` / `tool_max_threshold` 覆盖全局默认。

告警出现位置：

- 网关日志（带 server 名、可见数、阈值）；
- 管理台首页顶部横幅；
- Server 列表“工具 / 模式”列；
- `GET /mcp/discovery/servers` 的 `overWarn/overMax`；
- OpenAPI 批量导入响应里的 `warning`（导入后工具数超阈值时）。

## 5. 管理台操作

1. **新建 Server**：默认 `WHITELIST + DIRECT`，可在创建时切换。
2. **Server 详情 → 设置 → 工具暴露策略**：
   - 切换访问模式 / 暴露模式；
   - 设置告警/硬阈值；
   - META 模式下选择热工具，或点击「按调用记录推荐」（近 30 天成功调用 Top N）。
3. **应用与授权**：勾选 Server 会自动获得当前全部工具授权；白名单模式下新增工具需再次授权。
4. **首页 / Server 列表**：超过阈值会显示告警；点击可进入对应 Server 调整。

## 6. 管理 API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/mcp/admin/servers/budgets` | 全部 Server 的预算快照 |
| `GET` | `/mcp/admin/servers/{id}/tool-budget?appId=` | 单 Server 在指定应用视角下的预算 |
| `PUT` | `/mcp/admin/servers/{id}/tool-exposure` | 设置访问/暴露模式、热工具、阈值 |
| `GET` | `/mcp/admin/servers/{id}/hot-tools/recommend?days=30&limit=20` | 按成功调用推荐热工具 |
| `POST` | `/mcp/admin/tools/bulk-move` | 批量迁移工具到另一个 Server（拆分 Server 用） |

`PUT tool-exposure` 请求体：

```json
{
  "toolAccessMode": "WHITELIST",
  "toolExposureMode": "META",
  "hotToolCodes": ["order_query", "order_create"],
  "toolWarnThreshold": 100,
  "toolMaxThreshold": 500
}
```

- 阈值传 `0` 或 `null` 表示恢复全局默认；
- `hotToolCodes: []` 表示清空热工具；
- 热工具必须是该 Server 下启用工具，最多 50 个；
- 更新后会广播 `notifications/tools/list_changed`，已连接客户端会重新拉取。

拆分 Server 时可先创建目标 Server，再批量迁移工具：

```json
POST /mcp/admin/tools/bulk-move
{"toolIds":[28,29,30],"targetServerId":21}
```

限制：只能在同一业务方内迁移；目标 Server 不能是 MCP/聚合代理；同名工具冲突会整体失败；
迁移后工具级授权会被清除，需要在目标 Server 下重新授权。

| `MCP_TOOLS_CHUNK_STORE` | memory | `memory` / `redis`；redis 支持多副本 |
| `MCP_TOOLS_REDIS_URI` | redis://127.0.0.1:6379/0 | Redis 连接 URI（仅 chunk-store=redis 时使用） |
| `MCP_TOOLS_METADATA_ENRICH` | true | 离线元数据增强（code/name 拆词 + 中英同义词） |

## 8. 存量迁移与回滚

1. 执行迁移脚本（幂等）：

   ```bash
   mysql -u<user> -p mcp_gateway < db/mysql/migrations/20261018_tool_exposure.sql
   ```

   该脚本会补齐访问模式相关字段，默认值统一为 `WHITELIST`（fail-closed）。旧版本遗留的 `LEGACY` 取值在升级时请执行：

   ```bash
   mysql -u<user> -p mcp_gateway < db/mysql/migrations/20261020_unify_access_mode.sql
   ```

   脚本会把存量 `LEGACY`/空值统一归一为 `WHITELIST`，并修正列默认值与注释。

2. 观察 `tools/list` 的 `_meta.visibleTools` 与管理台预算，按应用补充 `app_tool_rel` 授权，或显式改为 `ALL`。

3. 如果 META 模式出现异常：

   - 单 Server：在管理台切回 `DIRECT`；
   - 全局：设置 `MCP_TOOLS_META_ENABLED=false` 并重启（或配置中心热更新，若已接入）。

4. 回滚代码时，新增列不影响旧版本读取（旧 SQL 使用显式列名）。

## 9. Schema 瘦身（E）

`tools/list` 与 `get_tool_schema` 默认会：

- 截断过长 `description`；
- 递归移除 `inputSchema` 中的 `examples` / `$examples` / `input_examples`；
- 默认去掉每个工具重复的 `server` 元数据。

这些字段对参数校验不是必需的，但往往占定义体积的很大一部分。

## 11. 2026-10-19 增强：从“能治理”到“可运营”

### 11.1 切换白名单的预检与补齐

- `GET /mcp/admin/servers/{id}/exposure-impact?targetAccessMode=WHITELIST`
  返回已授权应用、当前工具授权数、是否会失去工具。
- `PUT /mcp/admin/servers/{id}/tool-exposure` 支持 `backfillExistingApps=true`：
  切换为 WHITELIST 时，为已有 Server 授权的应用补齐当前全部工具。
- `POST /mcp/admin/servers/{id}/tool-grants/backfill`
  独立恢复入口，可按 `appIds` 指定应用。
- 控制台在切换时会弹确认框：「补齐并切换 / 保持空白名单切换 / 取消」。

### 11.2 分页兼容

- `mcp.tools.pagination-min-tools`（默认 500）：低于该值整包返回，避免不翻页客户端丢工具。
- `mcp.tools.pagination-clients`（默认 `codex,claude,dsh,cursor,workbuddy`）：客户端名称白名单。
- `mcp.tools.pagination-unknown-policy`（`PAGINATE` / `ALL`）。
- `_meta` 增加 `paginationUsed / paginationRisk / paginationThreshold / clientName`。
- `GET /mcp/admin/tool-pagination-stats`：cursor 发出、跟随、放弃计数；
  发出 cursor 后 10 秒未跟随会记 WARN 并计为 abandoned。

### 11.3 Token 预算语义

- `_meta.visibleTokens`：当前应用可见工具的总成本；
- `_meta.returnedTokens`：本次实际返回的工具成本（META 模式下通常只有几百 token）；
- `_meta.tokenizer`：`cjk-aware/approx-v1`（CJK 1 token/字，其他 4 字符/token）；
- `mcp_tool.token_estimate` / `tokenizer`：工具保存时预计算，`tools/list` 直接求和；
- `POST /mcp/admin/tools/token-estimates/rebuild`：存量工具重算。

### 11.4 检索增强

- 中文分词：单字 + 二元组（“订单查询”可命中“查询订单”）；
- 中英同义词：订单/order、退款/refund、查询/query 等；
- 热度加权：近 30 天成功调用次数，60 秒缓存；
- Embedding 混合检索：
  - 复用 `embedding.host/model/key`，OpenAI 兼容 `/v1/embeddings`；
  - 新表 `mcp_tool_embedding`，按 server 内存缓存 + 余弦相似度；
  - 工具创建/更新异步索引，`POST /servers/{id}/embeddings/reindex` 可重建；
  - embedding 不可用时自动降级到词法检索，不影响可用性。

### 11.5 应用级工具视图

- `app_server_rel.tool_access`：`INHERIT`（默认）/ `ALL` / `WHITELIST`，
  允许单个应用覆盖 Server 级访问模式，避免为“全部工具”写几千条 `app_tool_rel`。
- `app_server_rel.profile_tags`：应用级工具画像标签；
  非空时只保留 tags 有交集的工具，实现“同一 Server、不同应用看到不同工具集”。
- `PUT /mcp/admin/app-server-rels/{id}/access` 设置两项；
  控制台「应用与授权 → 展开 Server」可直接编辑。

### 11.6 拆分 Server 的 UI

- `ServerToolsTab` 支持多选工具 → 「移动到其他 Server」；
- 可选择是否「为原 Server 已授权应用补齐目标 Server 及被迁移工具授权」；
- 迁移后清理源 Server 的工具级授权与热工具残留。
